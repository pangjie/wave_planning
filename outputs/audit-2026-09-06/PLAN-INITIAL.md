### B1.1 本机访问控制

推荐方案：本地同源页面自动建立短期会话，不增加登录界面。

- 服务端以实际连接地址确认本机请求，Host 校验限定配置的本机地址与端口；不相信外部可伪造的转发头。默认本地策略拒绝远端业务请求，即使监听地址为 `0.0.0.0`。
- 业务 API 的读写及订单/PDF 下载都要求有效本机会话；会话通过受同源约束的启动握手建立。健康检查仅返回无敏感信息的存活状态。
- 修改接口额外校验完整 Origin（含端口）和防伪凭据；不以 CORS、SameSite 或固定请求头单独代替校验。跨域、`Origin: null`、其他本地端口不能借页面会话修改状态。
- 建议用 HttpOnly、SameSite 会话 Cookie 兼容现有下载链接；防伪值只留页面内存。会话按服务实例隔离，重启失效；不将长期密钥写入静态 HTML、URL、localStorage 或日志。
- 前端只保留一处本地 API 请求封装处理会话、错误及请求取消，禁止隐藏地重试创建/生成/拣货请求。服务重启导致会话失效时重新握手并恢复查询，不能重放操作。
- 本地命令行脚本与模拟测试使用同一会话握手契约。旧的裸敏感请求会被拒绝，这属于有意收紧的安全行为，需更新 API 文档。

威胁边界：防止外站、局域网设备误用本机 WMS 权限；**不声称防御同一操作系统用户下已经能读取进程/本地文件的恶意程序**。不建设多用户身份体系；以后需要共享访问时另行设计，不保留默认放行的“兼容后门”。

验收：Safari/Chrome 本机页面、普通下载、新标签页、不同端口、服务重启、离线 HTML；外站表单/脚本、恶意 Host、伪造转发头、无凭据和错误凭据请求均覆盖。UI 不多出无必要的确认步骤。

### B1.2 HTTP 依赖安全修复

- 在新的隔离环境中联合选择兼容的 FastAPI/Starlette；重新核对维护者公告及依赖约束后固定版本，不直接把 Audit 所列修复下限当成最终推荐版本。

- 不在正在提供服务的 `.venv` 中边运行边升级；部署时整体切换经过验证的环境。SheetJS 已排除的两项告警不触发无理由升级。

### B1.3 输入与文件上限

- 用最小分段请求模型替代任意字典；订单号必须为字符串列表。校验段标识及跨段重复订单，合法输入的归一化规则不变。
- 保留“超过多项搜索上限的段不自动多次生成”的行为；不借校验修改 700 单处理契约。

## 6. B3 — 生产结果、持久化与恢复

主要范围：[任务管理](/Users/jp/Documents/ChatGPT/波次规划系统改造/wms/project/backend/app/services/job_manager.py)、[波次记录](/Users/jp/Documents/ChatGPT/波次规划系统改造/wms/project/backend/app/services/wave_records.py)、[公共浏览器上下文](/Users/jp/Documents/ChatGPT/波次规划系统改造/wms/project/backend/app/automation/common.py)、四个工作流。

### B3.1 统一“已发生的业务结果”

以任务中的结构化分段/波次结果作为事实来源；事件消息只负责展示，wave-records 是可重建的索引，不再从日志字符串解析出另一份业务事实。

| 实际情况 | 处理规则 |
|---|---|
| 尚未提交，定位/验证失败 | 记录未执行；按原流程的停止/跳过策略处理 |
| 已提交，成功证据及波次号已取得 | 先记录结果，再做界面清理；保留计划数与实际核验数量的区别 |
| 成功已确认，清理失败 | 成功结果保留，附清理警告；不重新提交 |
| 提交可能已发生，但未能确认结果 | 明确“结果待核对”；不当成未执行，不自动重试 |
| 关键持久化失败 | 保留内存中已确认结果并告警，停止新增生产提交；已在途操作收集结果，不假定全部回滚 |
| 进程重启，遗留 queued/running | 终止孤儿运行状态，标明中断及确认程度；不自动恢复生产点击 |

优先保留既有顶层状态枚举，通过明确原因、结构化结果和警告补充语义；若确实需要新增状态，必须同批更新前端终态识别、API 测试和旧数据读取，不能只改后端枚举。

### B3.2 持久化与中断恢复

- jobs 与波次索引采用明确的原子写入策略；关键提交前意图和确认后的结果不受普通日志节流影响。
- 写入失败必须可见；损坏 JSON 保留原文件并停止覆盖，不能按空库继续。避免“修复吞错”后让回调异常把一个分段同时记成功、失败。
- 启动恢复先对遗留任务分类并落盘；孤儿取消也落盘。损坏文件不能被自动删除；需要核对的结果不显示成可无脑重跑。
- 不为跨文件一致性引入业务数据库：先保证任务事实原子保存，再更新可重建索引。索引失败不能丢掉已确认任务结果。
- 日志保留 job ID、阶段、脱敏异常链和关键计数；不写 cookies、token 或完整订单清单。

### B3.3 跨进程独占

- 对规范化的数据目录/profile 建立进程级租约，覆盖启动恢复、资料预处理、浏览器运行、结果写入到退出。共享 data 或 profile 的第二实例必须在任何写入前拒绝。

## 7. B4 — 计划身份与不可变导出快照

主要范围：前端状态与导出、生成任务 API、JobRecord、任务快照和波次索引。依赖 B3 的可靠持久化；B2 的请求代次直接复用。

推荐最小数据约定：

| 概念 | 用途与约束 |
|---|---|
| 批次标识 | 每次成功导入建立新批次；文件名相同不代表同一批次，导入失败不能误推进身份 |
| 计划版本 | 参数、选择、模式及导出顺序等改变后产生新版本，用于冻结任务输入和废弃旧异步响应 |
| 分段标识 | 依据批次、模式、渠道、类别和规范化订单集合生成；名称仅供展示，不能再作跨计划主键 |
| job ID | 唯一一次本地任务；结果及自动导出绑定这个任务，而非全局当前页面 |
| 导出快照 | 提交时冻结九个工作表所需的规范化订单字段、参数、选择、顺序及分段映射；不保存 DOM 或重复原 Excel 二进制 |

实现切片：

1. 前后端统一身份契约；后端校验订单集合并重新计算/核对分段指纹，不单信前端标签。结构化结果沿用同一标识贯穿 API→工作流→持久化→页面。
2. 任务提交前冻结导出快照，按 job 存为受大小限制的本地数据，保留 schema 版本；快照与任务意图可靠保存后才允许开始生产操作。继续使用现有 core 的规划/导出算法，不另写一套 Python 规划引擎。
3. 用户仍可操作页面；旧任务完成时只写回同一订单集合的分段。计划已变时仍能取得旧任务自己的导出文件，但不能用当前页面数据冒充旧计划。
4. 全局清理改为批次范围；GET/clear 响应校验发出时版本。更换批次不清除另一个标签页/任务的历史；显示顺序变化不应抹掉未变订单集合的波次证据。
5. 自动导出按 job＋快照版本幂等保存：重复完成响应、刷新或多标签页上传只返回同一个结果链接；显式手动另存仍沿用用户原有行为。上传响应丢失先查询保存结果，不能重复生成波次。
6. 刷新后从原任务快照恢复关联和导出，不从当时新页面反推旧计划。无身份的历史记录保留可查，但不得仅因“CBT/爆品1”同名就套到新批次。
